# 编辑手册

## 选题边界

服务于已经在构建 AI 应用的独立开发者和小团队。首批主题是文档与知识库、Agent 与工作流、上线与维护。新项目与成熟项目都可入选，不以 Star 排名代替判断。

## 每个项目的最低记录

1. 一句话实际用途与适合的任务。
2. 使用代价、限制和与现有方案比较的编辑判断。
3. 用户下一步可以完成的小型验证。
4. 官方来源、核查日期、验证程度。
5. 主题、可用的接入语言与部署路径。

`languages` 指本条目已核查的接入路径，不必等于仓库实现语言。未核查的路径不要为了提高匹配率而加入。`deployment` 为基础分类，不表示已测得完全离线或不产生外部 API 费用；相关限制必须写入正文。

初始内容基于 2026-10-22 查阅的官方 GitHub README，未安装运行所收录工具。内容中的比较与试验建议是编辑判断，不能表述成实测结论。

## 证据等级

- 资料核查：可定位官方来源，明确未实测。
- 安装验证：未来添加时须同时扩展记录，包含版本、系统、依赖、安装结果与复现步骤。
- 任务实测：在安装验证基础上增加样本、任务、结果、失败案例和适用范围。

不要只修改 `evidence` 标签就声称完成实测。

## 新一期的发布流程

1. `npm run collect` 收集候选，或人工从官方仓库补充候选。
2. 审核并编辑 `content/catalog.json`。候选数据不会自动入库。
3. 添加唯一刊物 ID、发布日期与项目引用。程序按日期倒序排列，同日按 ID 倒序排列。
4. 运行测试，检查网页样刊、项目详情与邮件样稿。
5. 提交并部署内容，重启服务。
6. 在 `/admin` 预览匹配人数，确认后批准本期。预览不创建邮件或令牌；批准绑定具体内容，后续修改使原批准失效。
7. 手动投递或由启用后的周五定时任务投递。

同一订阅者、同一期只创建一个周报记录。修改已发送刊物不会自动重发，重大勘误应使用新的刊物 ID 并解释原因。

## 元数据与公开发现

运行 `npm run refresh:metadata` 获取已收录项目的官方 GitHub API 快照。核查 `content/github-snapshots.json` 差异后再提交。失败时保留旧值与旧采集日期，不以本次执行时间掩盖过期数据。网页会提示超过 30 天的快照；API 没有返回 Release 时显示未获取，不能据此判断项目没有其他发布渠道。

快照中的 Star 只供参考，不参与匹配或排序；归档项目排除出公开筛选与邮件匹配，但保留历史文章及详情。未归档、最近推送或有许可证识别结果，都不等于已证明可靠、适合生产或适用于某项商业用途。详情提供原始来源供读者核查。

元数据属于项目内容的一部分，刷新会使相关刊物的已有批准失效，需重新预览并批准。刷新不会自动发布新刊，也不会向关注者发送版本提醒。

比较页中的 `kind` 表示工具在流程中的角色。不同角色的项目往往互补，不能包装成同类性能比较；适用条件与试验建议属于编辑判断。公开 RSS 只包含已发布刊物，主题 RSS 收录包含该主题项目的整期内容。

## 反馈与四周验证

初始建议招募 20～30 位主动订阅者。观察连续反馈、已使用项目、回访与选型需求，不以收藏或打开量作为唯一成功标准。反馈每个用户每个项目只有一个当前值，更新不会虚增人数。

关注项目当前只保存列表，不自动监测或推送版本变化。不要在宣传中暗示该功能已经上线。
